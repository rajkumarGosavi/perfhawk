# V5 "Time" Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add time to profiles: a time heat map per profile with range selection that drives the flame/top/call views, a second range as a baseline for a window-vs-window diff (C1), and a session timeline with one sparkline per captured kind where clicking a spike zooms everything (C3). Time-aware capture comes first, because today's stored profiles are aggregated and have no timestamps.

**Architecture:** Timestamps live in a **sidecar** (`Timeline`: a bucket index per sample) stored next to the profile blob, so existing bincode blobs stay readable and no migration runs. `Filter` gains an optional time range so every existing analysis (flame, top, sandwich, groups, graph, findings, diff) works on a window for free. Capture produces timelines by two routes: .NET EventPipe samples already carry timestamps (helper change); Go gets windowed CPU capture (many short pprof windows stitched into buckets). A spike task decides and records feasibility before any capture code is written.

**Tech Stack:** Rust (`perfhawk-model`, `perfhawk-store`, `perfhawk-analysis`, `perfhawk-server`, `perfhawk-capture`), Go agent, .NET helper, React 19, TypeScript, SVG/canvas, vitest. **No new dependencies** (the heat map is drawn on a plain canvas).

**Spec:** [docs/VISUALIZATION.md](../../VISUALIZATION.md) §4 C1, C3, §6 (data-model prerequisites: bucketed timeline; heat map ≤ 1 s for a 1 h capture), §7 (V5), §9 Q2 (bucket size and where computed). Builds on V2–V4. **C2 (per-thread/goroutine tracks) is deferred** to the Phase 2 `Timeline` kind with events ([PLAN.md](../../PLAN.md) §196); it needs thread/state events this plan does not capture.

## Global Constraints

- No new dependencies. Existing stored profiles and the existing store schema keep working untouched (`SCHEMA_VERSION` may add a column/table only if Task 2's design requires it, with a forward migration and a refusal path for newer versions as today).
- **Bucket size ruling (Q2):** timelines are bucketed at **capture time** into `bucket_ns` = 20 ms for CPU/wall (configurable later), stored as `u32` bucket indexes; query time never needs raw events.
- Heat map query ≤ 1 s for a 1 h capture at 20 ms buckets (180 000 columns collapse to ≤ 1 200 display columns server-side); window queries add ≤ 300 ms to an equivalent unwindowed query (manual check).
- Profiles without a timeline show no time UI and every time endpoint answers `404 no_timeline` (a clear error code), never an empty heat map.
- Every view state in the URL (`t0`, `t1` window; `b0`, `b1` baseline), keyboard operable range selection, text equivalent for the heat map (a table of the selected window's start/end and sample count).
- Green after each task: `cargo test --workspace`, `cargo clippy --workspace -- -D warnings`, `go test ./...` in `agents/go`, the helper's tests under `helpers/perfhawk-dotnet/tests` where affected, and in `ui/`: `npm test`, `npm run lint`, `npm run build`.

## Review Focus

- A profile recorded before V5 (no sidecar) opens normally everywhere; the Summary hides the time controls and `/heatmap` returns `404 no_timeline`.
- A window that contains no samples, a window with `t1 <= t0`, and a window entirely outside the capture: flame says "No samples in this view.", the API answers 400 only for `t1 <= t0`, never `NaN`.
- A 1 h capture at 20 ms (180 000 buckets × many stacks): the heat-map response stays under 1 MB and the UI draws without freezing (decimation is server-side).
- A corrupt or truncated sidecar: the profile still loads without time (logged warning), it does not fail the whole profile.
- Go windowed capture where a window yields zero samples (idle process): the bucket exists with value 0 and the heat map shows an idle column, not a gap or a crash.

### Task 3: Time window in the analysis engine

**Files:**
- Modify: `crates/perfhawk-analysis/src/filter.rs`, `crates/perfhawk-analysis/src/lib.rs`, `crates/perfhawk-analysis/src/tree.rs` (skip the unfiltered fast path when a window is set), `crates/perfhawk-analysis/tests/analysis.rs`

**Interfaces:**
- Produces:
  - `Filter` gains `pub window: Option<Window>` with `pub struct Window { pub timeline: Arc<Timeline>, pub from_bucket: u32, pub to_bucket: u32 }` (half-open `[from, to)`); `Filter::with_window(self, Window) -> Filter`; `is_empty()` is false when a window is set. `for_each_sample` skips samples whose bucket is outside the window (before exclude/focus/hide).
  - `pub struct HeatCell { col: u32, row: u32, value: i64 }`; `pub struct Heatmap { bucket_ns: u64, start_unix_ns: i64, cols: u32, rows: u32, col_buckets: u32, row_buckets: u32, cells: Vec<HeatCell>, max: i64, total_buckets: u32 }` (camelCase serde).
  - `pub fn heatmap(p: &Profile, t: &Timeline, sample_type: usize, filter: &Filter, max_cols: u32) -> Heatmap` — FlameScope layout: a column covers `col_buckets` consecutive buckets and its rows are the offsets inside that span. `col_buckets` is the smallest value ≥ `1 s / bucket_ns` (50 at 20 ms) such that `cols = ceil(total_buckets / col_buckets) ≤ max_cols`; `rows = min(col_buckets, 50)`, merging adjacent buckets into a row when `col_buckets > 50` (`row_buckets = col_buckets / rows`, rounded up). Only non-zero cells are returned; `max` is the largest cell.

## Rulings made while planning

- **Sidecar, not a model change:** `Profile` is stored as bincode, which is not self-describing; adding a field would invalidate every stored blob. A separate timeline file avoids a migration entirely.
- **Capture-time bucketing (Q2):** 20 ms buckets are decided at capture time so the store never holds raw events and the heat map is a histogram query.
- **Go via windows:** pprof CPU profiles carry no per-sample time, so Go resolution is limited by window length (from the Task 1 spike); the UI states the resolution rather than implying 20 ms precision.
- **C2 deferred** until the Phase 2 event timeline exists; V5 only needs per-sample buckets.
- **Gate:** Task 1 can stop the plan; Tasks 2–4 and 6–7 are still useful for imports that carry time, but Task 5's capture value depends on the spike.
